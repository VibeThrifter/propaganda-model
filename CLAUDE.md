# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A research database modelling the structural mechanisms that filter and shape Dutch news media, based on Herman & Chomsky's propaganda model (*Manufacturing Consent*, 1988) applied to the Netherlands. The domain — entities, roles, mechanisms, argument text, and all documentation — is in **Dutch**. Match that language when adding seed data, API messages, or docs. `DOCUMENTATIE.md` is the authoritative domain spec (the five filters, scoring rubric, entity/relation types, schema reference).

It is a research/analysis model, not a conspiracy theory: it describes pro-elite bias as an *emergent* property of structural forces. Keep that framing in any generated content.

## Stack & commands

Plain Python 3 + SQLite + Flask. No build step, no test suite, no linter, no `requirements.txt`. Flask is the only third-party dependency (`pip install flask`); everything else is stdlib.

## Architecture: three layers in one SQLite DB

The whole model lives in `data/propaganda_model.db` (gitignored). Understanding the layering is the key to working here:

1. **Theoretical model (abstract, no names)** — `roles` (functions like `mediaeigenaar`, `gatekeeper`) and `mechanisms` (processes like `pakketjournalistiek`, `zelfcensuur`). Each mechanism has a primary `filter` (Eigendom, Advertentie, Sourcing, Flak, Ideologie, `tegenmacht`, `overig`) plus optional extra filters (`mechanism_filters`) and cross-cutting themes (`mechanism_themes`), and an **`aard`** that says how real a dyadic edge is — see "Derived layers" below. All three theory tables (`roles`, `mechanisms`, `emergent_effects`) also carry optional `active_from`/`active_until` mirroring the practice layer (NULL = unbounded as far as known; only set for evidently technology-/bestel-bound elements — see `migrate_tijdsdimensie_theorielaag.py`). The viz timeline slider filters **both** models by these fields (looptijd is discussable per mechanism/role in the detail panel); `scoring.py`/`influence.py` still ignore them — evidence counts timelessly.
2. **Instance model (concrete, named)** — `entities` (DPG Media, specific people) each linked to roles via `primary_role_id` and the `entity_roles` join; `relations` between entities, each optionally tied to a `mechanism_id`. **An entity's *displayed* primary role/filter is derived, not the stored `primary_role_id`** — `scoring.py` picks the filter with the largest Σ(certainty × influence) over the relations the entity is the **source** of (see "Derived layers"); `primary_role_id` is only fallback/override (entities without a sourced relation) and still the handle `influence.py` uses to find target sets (`publiek`, `politicus`). Every relation carries **two independent scores**: `certainty` ("does this relation exist?") and `influence` ("how strongly does it shape coverage?"). A relation can be certain but low-influence (passive shareholding) or uncertain but high-influence (self-censorship). See `DOCUMENTATIE.md` for the scoring rubric.
3. **Evidence / discussieboom** — `sources` (+ `source_locations` for url/doi/isbn/etc.), `arguments`, and `citations`. `arguments` form a **tree**: `parent_argument_id` NULL = root, otherwise a reply; each argument targets a `relation_id`, `entity_id`, `role_id`, `mechanism_id` or `emergent_effect_id` (at least one required — the theory targets carry the literatuuronderbouwing) and has a `stance` of `supporting` / `contradicting` / `contextual`. `citations` attach quotes from sources to arguments. `edit_log` audits argument creation and status changes.

## Derived layers: scores, influence graph & the `aard` visual vocabulary

Two pure-stdlib modules at the repo root turn the raw model into derived numbers; both are shared by `generate_viz.py` and the `/api/scores` endpoint.

- **`scoring.py`** — credibility & strength of theory elements, built bottom-up from the discussieboom (argument evidence → per-relation/-entity practice score → per-role/-mechanism theory score, combined with literature via noisy-OR). **Scoring v2 (fase 1)** adds: DF-QuAD tree propagation (M1.1 — replies carry **no own target** by DB CHECK; a contradicting reply is an *ondergraving* — the "logica klopt niet"-verdict — that dampens only its parent's σ; only root arguments count toward the target. **Review-verdict v2:** every contradicting reply requires `reasoning` and carries a resolution loop `bezwaar_resolutie` ∈ {open, herzien, blijft, opgelost}; only an `opgelost` bezwaar stops damping (`update_bezwaar_resolutie` in server.py — author marks `herzien`, the bezwaarmaker re-judges `opgelost`/`blijft`, a reviewer may overrule to `opgelost` only after `herzien`; `scripts/test_bezwaar_resolutie.py`)), source clusters (M1.2 — `sources.cluster_key`; within a cluster only the strongest argument counts, uncited args share one pseudocluster; reliability class `eigen_synthese` weighs 0), 95% intervals (M1.3 — Beta on layer B, bootstrap on layer C; no evidence = 0 without uncertainty), the contradiction cap (M1.4 — without a sourced, non-rejected counter-argument credibility is capped at 0.70 + flag `onweersproken`; also applies to priors), emergent-effect scores (M1.5 — literature ⊕ **compositieclaim** `property='compositie'`, capped at 0.50 without one), and an evidence line for the influence axis (M1.7 — `property='influence'` arguments shift derived influence/mechanism sterkte; aspect arguments never count in the certainty balance). **Both axes are guilty-until-proven:** an un-evidenced prior is floored to 0.05 and only acts as a fallback — `certainty` via `migrate_unsourced_certainty.py`, `influence` via `migrate_unsourced_influence.py` (floor 0.05 chosen over 0 so `influence.py` still measures topology while magnitude stays minimal until proven); the validator's `INVLOED-PRIOR` check (a `fout`, ratcheted) guards that any influence above the floor carries a `property='influence'` argument. Output keeps `relations`/`entities` as plain maps and adds `*_detail`, `relations_influence`, `emergent_effects`, `argument_scores` (τ/σ), and `entity_primary_filter`/`entity_filter_scores` (the **derived primary role**: argmax filter over Σ(certainty × influence) of the relations each entity is the *source* of — source of truth for viz colour/category, with `primary_role_id` as fallback; classification uses magnitude so tegenmacht counts positively here, unlike the influence graph). **Self-reported `weight` is neutralized:** the stored `weight` column no longer feeds the score (it was the contributor's own number — Z2), so τ = `statusfactor × bronfactor` (neutral weight 1.0), where **bronfactor = reliability-rigueur × relevance** — the relevance factor comes from `sources.onderwerp` (`nl_systeem` ×1.15, `buitenlands` ×0.85, `algemeen`/`onbepaald` ×1.0, capped at 1.0) so a Dutch-media source outweighs a foreign one at equal rigour; classifying a source (reliability + onderwerp) is **reviewer-gated** via `PATCH /api/sources/<id>/classificatie`, guarded by `validation.klasse_consistentie` (type↔class + a locator for high classes) and audited by the `BRON-KLASSE` check. A bijdrager (incl. agents) may **propose** a classification (`reliability_voorgesteld`/`onderwerp_voorgesteld` via `POST /api/sources` or `PATCH /api/sources/<id>/classificatie_voorstel`) — advisory only, it **never feeds the score** (`scoring.py` reads only the authoritative `reliability`/`onderwerp`); the reviewer's confirmation copies it over and consumes it (mirrors voorgesteld→merged). A **bridged rating** (M2.5) fills weight back in objectively once a rater pool exists (review-verdict v2: +1 = 'Logica klopt', −1 = a maintained ondergraving; `bridging.py` shrinks toward neutral 1.0 with α = n/(n+k), no threshold cliff). Net: no score input is self-reported anymore — certainty/influence come from evidence (priors floored to 0.05), argument strength from status + source + bridged judgment. `compute_all_scores(conn, exclude_cluster=…, bridged_weights=…)` powers the leave-one-cluster-out analysis; the optional bridged-weights map (M2.5, loaded from `data/bridging.json` via `bridged_weights_from_file`) overrides the neutral `weight`. **Fase 2:** arguments with status `voorgesteld` count in *nothing* (not even the contradiction balance) until merged, and `vervangen` elements (M2.6) are skipped by `scoring.py`, `influence.py` and the viz alike — **the same now holds for `vervangen` *arguments*** (those superseded by a revisie: `scoring.py` selects `WHERE NOT vervangen`, so an opvolger never double-counts with the argument it replaces). Golden snapshot: `scripts/test_scoring.py` (runs inside `validate_model.py --strict`); the worked examples live in `DOCUMENTATIE.md` § "Scores: van discussieboom naar theorie".
- **`influence.py`** — a directed, weighted influence graph (`source --influence--> target`). Measures structural *position* (direct / transitive / reach / influence-on-public), not intent. `scripts/analyze_influence.py` gives rankings and `--path "A" "B"` traces the strongest (max-product) cascade between two entities — each hop multiplies a weight <1, so a mediated chain comes out small (the "small systemic effect").

**`mechanisms.aard`** (relations inherit it) classifies *how real* a dyadic edge is, and drives **both** the influence math and how the edge is drawn. **Guiding rule: an edge between two nodes is `direct`** — "indirectness" is a property of a *path*, not of a single edge. The live model has only two edge kinds — `direct`, and the `veld_eigenschap` **halo** (a property of the *target* node, drawn as a ring, not counted as outgoing influence; `source_role_id` may be `NULL`) — plus the separate `emergent_effects` **hyperedge** (a translucent gold field over a *group* of roles; own tables `emergent_effects` + `_members` + `_subeffects`). Emergent fields are **first-class theory elements**: own discussieboom (`arguments.emergent_effect_id`), own time window, and an own score (lit-only — no practice layer; `scoring.py` key `emergent_effects`). The apex field `fabricage_van_instemming` carries the eleven other fields as formal **deel-effecten** (`emergent_effect_subeffects`); its member set stays pars pro toto (one carrying role per filter + medium + publiek). Two older kinds, `indirect` and `veld_instantiatie`, are **deprecated and empty**; their viz rendering is gone, so a mechanism set to those now just draws as a plain direct edge. The full conceptual definitions, influence math, and worked examples live in `DOCUMENTATIE.md` § "Aard: direct & systemisch" — that is the single source of truth; don't duplicate it here.

**Afgeleide (indirecte) pijlen** are never stored: the viz derives them at node-selection time and shows one only if (1) every hop clears the support gate, (2) every hop has its own discussieboom arguments, and (3) the *composition* is backed by a **padclaim** — an `arguments` row with `role_id` = source role, `property='indirecte_invloed_op'`, `property_value` = target role **ID** (rename-proof since M2.6; excluded from role scores by `scoring.py`; practice layer matches via the entities' roles). Per-hop support does not imply the composite claim. See `DOCUMENTATIE.md` § "Afgeleide (indirecte) pijlen & padclaims".

**When adding a mechanism, choose `aard` in this order:**
1. Standing *state of one node* with no attributable live sender (causes may exist but are diffuse/overdetermined; the state keeps operating without live input — e.g. self-censorship)? → `veld_eigenschap` (`target_role_id` = that node; `source_role_id` the diffuse origin or `NULL`). Never re-model it as an (incoming) edge: its causes already have their own edges, so that would double-count the same force.
2. Property of a *group* of roles with no single sender — including feedback loops between multiple roles, where every link is both cause and effect? → an `emergent_effects` hyperedge, not a mechanism row.
3. Otherwise a relation between two specific nodes → `direct` — even when the influence is **mediated** (draw the intermediary chain; `influence.py`'s max-product damping makes the net effect small) or **diffuse/uncertain** (encode that in the `certainty` score, not a dashed line).
4. Don't reach for `indirect`/`veld_instantiatie`.

Viz/code notes: the **"Systemische effecten"** panel has separate toggles per layer: gold emergent fields (`state.showFieldEffects`) and halos (`state.showHalos`, also switches node size to the `_veld` variant) are theory-model only (the practice model draws every relation as a normal edge); derived arrows (`state.showDerived`) and direct edges (`state.showDirect`, drawing only — nodes/derived paths/stats keep following the real filters) work in both models. The live DB's `aard` column has **no CHECK** (added via `ALTER TABLE`); the CHECK lives only in `schema.sql` (it still lists all four values — the two deprecated ones retained for migration replay), so changing the enum is a plain `UPDATE` in a migration plus a `schema.sql` edit for fresh builds. Migration trail that collapsed everything to the live set: `migrate_reclassify_indirect_to_direct.py`, `migrate_field_to_direct_dyads.py`, `migrate_reshape_hegemonische_to_frame_export.py`, `migrate_genericize_elite_frames.py`, `migrate_sociologische_homogeniteit_halo.py`, `migrate_frame_export_to_halo.py`, `migrate_tier_herindeling.py` (tier audit: duplicate halos/dyad absorbed by their hyperedges; feedback loop → hyperedge).

anders mag de *auteur* z'n eigen nog-`voorgesteld` entiteit bijschaven — incl. de **rol-suggestie** `primary_role_id` — zodat de scout zelf een rol voorstelt i.p.v. die leeg te laten) + **`POST /api/{entities,relations}/<id>/heraanmelden`** (afgewezen praktijkelement opnieuw indienen), DELETE for roles/mechanisms), the proposal system (`/api/voorstellen` GET/POST + `/reviews` + `/intrekken` + **`/herzien`** (afgewezen/ingetrokken voorstel verbeterd opnieuw indienen), `/api/review_queue` (+ `herkeuring`-lijst van betwiste argumenten; elk argument draagt een `thread_param`/`thread_id`-anker)), **`/api/mijn/bijdragen`** (werkbank, `@require_user`) achter de pagina **`/werkbank`**, `/api/recent_changes` + `/api/watchlist` (M2.4), `/api/lineage/<type>/<id>` (M2.6), the voorspellingsregister (M3.4: `GET/POST /api/predictions` — claim/afleiding/meetcriterium/kans + deadline **in de toekomst** + ≥1 theorie-anker verplicht; `PATCH /api/predictions/<id>/uitkomst` = reviewer+, berekent Brier, alleen vanuit `open`, zelf scoren gevlagd `self_scored`), `/api/health` (M0.5, reuses `validation.py`; carries `onderzoeksagenda`/`gevoeligheid` JSON-rapporten and the newest `release` when present), **`GET /api/agent/reeds_gereageerd`** (@require_user — de argument-id's waar het ingelogde account al op reageerde, via reply of rating; een agent haalt dit vóór een ronde op en slaat die argumenten over zodat hij niet twee keer op hetzelfde argument reageert. Geen eigen tabel — afgeleid uit `arguments.parent_argument_id`/`contributed_by` + `argument_ratings`. Backstop: `POST /api/arguments` weigert een tweede reply van een **agent**-account op dezelfde parent met **409**; mensen mogen wel meerdere reacties), `/api/scores`, and the visualisation at `/`. Opens a fresh SQLite connection per request with `PRAGMA foreign_keys = ON`. All writes are logged to `edit_log`.
- **Identity & gates (M0.6/M2.1).** Reading is open; *every write endpoint requires a user* (table `users`, managed via `scripts/create_user.py`; login portal at `/login`, account page + token rotation at `/account`). Auth is session (`/api/login`, humans with password) or `Authorization: Bearer <token>` (agents and Claude Code; token files live in `data/tokens/`, gitignored, only the sha256 hash is stored). Attribution always follows the logged-in user — `contributed_by`/`changed_by` are FKs to `users` since M2.1 (historic tags got inactive legacy accounts). Role ladder `bijdrager < reviewer < maintainer`, plus per-filter roles (`user_filter_rollen`, `create_user.py --filter-rol sourcing=reviewer`): the effective role within a filter is max(global, filter role). Status PATCH and merges need (effective) reviewer+; DELETEs need maintainer; **nobody verifies their own work** (403 — M2.1). Per-account rate limits on writes (M2.4: 30/60/120 per minute by role) and difflib duplicate detection on new root claims (409 + kandidaten; override with `negeer_duplicaten`). **Admin-beheer van bot-werk (agent-scope).** A maintainer fully manages **agent-authored** content but **never silently rewrites another human's contribution** — a human keeps their own work (a mens edits via `/werkbank`; the admin merges/rejects/deletes but doesn't overwrite their words). The agent-scope gate (helpers `_is_agent` / `_maintainer_mag_direct`: author *or* maintainer-if-author-is-agent, plus the maintainer's own / seed-with-no-author) applies to **in-place edit of a `voorgesteld` argument** (`PATCH /api/arguments/<id>`), **heraanmelden** of a rejected entity/relation, **herzien** of a rejected RfC, and **direct PATCH of an entity/relation** (`patch_entity`/`patch_relation`; the shared theory-layer `_maintainer_patch` is unaffected). Maintainer-only, *not* agent-scoped (any author): **heropenen** a `verworpen` argument (`POST /api/arguments/<id>/heropenen` → voorgesteld) and **hard delete** of rejected items — `DELETE /api/arguments/<id>` (only `verworpen`, refuses non-verworpen children), `DELETE /api/voorstellen/<id>` (only afgewezen/ingetrokken; `voorstel_reviews` cascadet via FK), and the existing entity/relation DELETE (any state). Hard delete breaks the otherwise-universal "niets wordt verwijderd"-regel (status flags + lineage) and is bounded to rejected/withdrawn states; the `edit_log` keeps a `deleted` row. The rejected backlog is visible at `/overleg` → tab *Voorstellen* → pill **Afgewezen** (`GET /api/afgewezen`, reviewer+), each item with its rejection feedback + verbeter/verwijder-knoppen (knoppen verborgen waar ze tóch 403 zouden geven). A separate read-only **reviewbeoordelaar**-agent (`missies/reviewbeoordelaar_brief.md`, no token) writes `data/review_advies.json` (gitignored) that `/overleg` renders as a per-item advice panel beside the queue (`GET /api/review_advies`, reviewer+; advisory, telt nergens mee). **Bron-suggesties (two-stage, advisory):** the documentalist (bron-agent) searches sources for problem-arguments — rejected ones (`GET /api/afgewezen`) and sourceless submitted roots (`ongesourcet_root`) — and writes `data/bron_suggesties.json` (gitignored) keyed `arg:<id>` with proposed sources (titel/url/waarom/quote); the **reviewbeoordelaar** then web-verifies each and fills a `check` verdict (klopt/twijfel/klopt-niet). `/overleg` shows both in the right column beside the argument (`GET /api/bron_suggesties`, reviewer+; advisory, telt nergens mee — the admin uses them to improve/heropen the argument, nothing enters the model automatically). Each suggestion carries a reviewer+ **"+ Bron toevoegen"** button that actually adds it under the admin's own account: `POST /api/sources` (title + url-locator, `source_type` from the suggestion else `website`) then `POST /api/citations` attaching it to that argument — a sourceless `voorgesteld` root becomes citable/mergeable in one click (still a human decision; the bron-agent only proposed).
- **Voorstel-workflow (M2.2/M2.3).** Every argument lands as `voorgesteld` and counts in nothing until a reviewer merges it (`POST /api/arguments/<id>/merge`). The M0.3 citatiepoort is now a **hard block at creation** for supporting/contradicting **roots**: `POST /api/arguments` requires ≥1 *echte* citation inline (a quote, or a source with a locator) or returns **400** — un-sourced evidential claims can't enter the model at all. Only the kinds that actually move the certainty balance are gated — plain evidence (no `property`) and influence-evidence (`property='influence'`); **exempt** (they don't weigh in the balance): replies/ondergravingen, contextual roots (*duiding* — `contextual doet niets`), and classification/structural aspect roots (`property` = `filter`/`mechanism`/`compositie`/`indirecte_invloed_op`). The older **merge-time** gate remains a backstop for any legacy un-sourced root: a supporting/contradicting root with an *echte* citation → `ongecontroleerd`, without one → `bronvermelding_nodig` (statusfactor 0.40 vs 0.50 = a score penalty). An **echte citation** carries a quote *or* its source has a locator (`source_locations`); a bare title-stub does not (same rule in `POST /api/citations` and the new `PATCH /api/citations/<id>`). The review card (`/overleg`) renders each citation (quote + source as clickable link + `[archief]`) and badges unsourced roots (`ongesourcet_root`) so the gate is legible *before* the merge click; the viz does the same link rendering. Locators can be added to an existing source via `POST /api/sources/<id>/locations`. Self-merge allowed but flagged `self_merged`. `GET /api/arguments/<id>/score_diff` previews the score impact on a temporary copy. New theory elements arise **only** via RfC (`POST /api/voorstellen`, soort `nieuw_theorie_element`; direct roles/mechanisms POSTs return 403): the template demands definitie, aard + freeze-test, afgrenzing, falsificatiecriterium, ≥1 instantiatie, ≥1 bron; acceptance needs **two human reviewer akkoorden** (submitter excluded; agent reviews are visible advice but never count), practice-layer proposals need one. Splitsen/samenvoegen/hernoemen (M2.6) run through the same proposal path with mandatory hertriage (see `voorstellen.py`; nothing is deleted — `vervangen` flag + `lineage`). **Argument-revisie-lus (Fase A–E):** a `voorgesteld` argument the author may edit in-place (`PATCH /api/arguments/<id>`, telt nog nergens); a *merged* argument is frozen and improved via a **revisie** — a new `voorgesteld` argument that on merge **supersedet** the old (old → `verouderd` + `vervangen = 1`). Arguments supersede via a **self-pointer** (`arguments.reviseert_id` + `vervangen`), **not** the `lineage` table (whose `voorstel_id` is `NOT NULL` and argument-merges don't go through `voorstellen`). A reviewer can send a merged argument back to **herkeuring** (`status='betwist'` + verplichte motivatie) after a bad rating/drogreden; it resurfaces in `review_queue.herkeuring`. The threads view shows a poort-statusbadge + inline merge/afwijzen/bewerk/reviseer/herkeuren, the review card embeds the surrounding thread (read-only, mét 👍/👎-advies), and **`/werkbank`** shows a user their own work per status with the received feedback and verbeter-/opnieuw-indien-knoppen. **Reply rules (M1.1/M1.8):** a reply carries no target and no property (400 otherwise); contradicting replies (ondergravingen) may be sourceless and can carry an `objection_type` (drogreden taxonomy; see `missies/monitor_brief.md`) — a set `objection_type` **requires `reasoning`** naming the contested step (400 otherwise; a bare fallacy-label is itself a loze aanklacht). Agent missions (monitor/scout/red team) run as Claude Code sessions under their own agent accounts with briefs + audit logs in `missies/` (M1.8/M1.9/M3.3); the scout picks its topic from `data/onderzoeksagenda.json` (M3.2), the red team its targets from the `redteam_top20` list in the same file. `missies/audit_checklist.md` holds the yearly-audit checklist (M3.5, next: June 2027).
- `web/template.html` is the **source** for the visualisation. `web/index.html` (~580 KB) is **generated** by `scripts/generate_viz.py`, which injects the DB data as JSON into the template. **Do not hand-edit `web/index.html`** — edit `template.html` (or the generator) and regenerate.

### How a bot contributes through the API (agent-contract)

A bot — the monitor/documentalist/criticus missions, or Claude Code itself — works the model exactly like a human contributor: through the REST API, **never** by writing to the DB or running a migration for content. The per-mission brief lives in `missies/*.md`; this is the shared contract they all build on.

- **Auth & identity.** `GET` endpoints are open and need no token — find target ids straight from the DB or the JSON baked into `web/index.html`. Every write sends `Authorization: Bearer <token>`, read from `data/tokens/<account>.token`, under the bot's **own** agent account (`bijdrager`) — never the owner's account or token (that would make attribution lie *and* skip the gates). `contributed_by`/`edit_log` then follow the account automatically.
- **You propose, a human decides.** Everything a bot submits lands as `voorgesteld` and counts in *nothing* until a human reviewer merges it (M2.2). A bot **never** changes status, merges, classifies a source, or deletes — those are reviewer+/maintainer *and* human-only (403 on your own work regardless). Stay inside: new arguments, citations, sources + locators, ratings, **instance-layer entities + relations** (they land `voorgesteld` and need one human reviewer — the `scout` mission, `missies/scout_brief.md`), and — for anything *theory*-layer (new roles/mechanisms/emergent fields) — an RfC. Log each mission round in `missies/logs/`. **An agent reacts at most once to the same argument** (only one of each agent type runs at a time, so concurrency isn't the worry — re-runs over time are): fetch `GET /api/agent/reeds_gereageerd` first and skip those argument ids; the backstop is a **409** on a second agent reply to the same parent (see `missies/README.md`). **Negative search results stay in the mission log, never as a `contextual` model contribution** — an AI's unverifiable "searched, found nothing" doesn't lift `onweersproken`, moves no score, and as a model node only manufactures false reassurance; in the log it does its one real job (proving a broad, non-cherry-picked search).
- **`POST /api/arguments` has two shapes.** A **root** (a claim *about* a target) carries `claim` + `stance` + exactly **one** target id (`relation_id` | `entity_id` | `role_id` | `mechanism_id` | `emergent_effect_id`); a `supporting`/`contradicting` root is **hard-gated** for evidence — it must carry ≥1 *echte* citation inline (`citations: [{source_id, quote, …}]` with a quote, or a `source_id` whose source has a locator) or the API returns **400** (`contextual` roots are exempt). Register the source first (`POST /api/sources` → `POST /api/sources/<id>/locations`); a bare title-stub is not a real source. A **reply** (relative to a parent) carries `parent_argument_id` + `claim` + `stance` and **no** target and **no** `property` (400 otherwise); a `contradicting` reply is an *ondergraving* and **requires `reasoning`** naming the exact contested step (`objection_type`, a drogreden-label, is optional but also needs `reasoning`). Ondergravingen may be sourceless.
- **Stance follows the evidence's effect on the *target claim*, not your overall sympathy.** This is the rule bots get wrong most. Counter-evidence to a claim is its **own contradicting argument on that claim** — never a "maar let op, dit pleit ertegen"-zin folded into a *supporting* argument. The DF-QuAD engine (M1.1) only weighs what is a *separate node*: a caveat buried in a supporting root adds to the *vóór*-kant (it pushes the claim **up** — the opposite of what you meant) and leaves the target falsely flagged `onweersproken`, so the contradiction cap (M1.4) never lifts. The *same fact* legitimately plays opposite roles on different targets — e.g. PAX' F-35-rechtszaak tegen de Staat **supports** the tegenmacht-relatie (rel. 472) and **contradicts** the zelfcensuur-relatie (rel. 482). Pick the form by what the evidence is: a **weerlegging** (you hold counter-*evidence* with a source) → a `contradicting` **root** on the target, *with* citation; an **ondergraving** (the inference is invalid; no counter-source needed) → a `contradicting` **reply** with `reasoning`. (Detail in `missies/monitor_brief.md`.)
- **Other gates to expect.** `weight` is ignored (Z2 — self-reported, neutralised); don't set it. New root claims hit difflib duplicate detection (~0.85 similarity → **409** + `duplicaat_kandidaten`; resubmit with `negeer_duplicaten=true` only if genuinely new). Writes are rate-limited per account (30/60/120 per minute by role). New theory elements (roles/mechanisms/emergent fields) are **never** created by a direct POST (403) — only via RfC (`POST /api/voorstellen`, soort `nieuw_theorie_element`, full template + ≥1 instantiatie + ≥1 bron), which needs two human reviewer akkoorden.

#### Elementvoorstellen op verzoek (als de eigenaar mij vraagt elementen te suggereren)

Boven op de API-mechanica geldt deze **modelleerdiscipline** (uitgekristalliseerd in de PAX-draaideur-discussie, juni 2026). Pas 'm toe vóór je iets indient:

1. **Elke *goedgekeurde* praktijkrelatie is een instantie van precies één mechanisme** — direct, tussen twee concrete knopen, met `mechanism_id` gezet (een mechanisme ís een gerichte theorie-edge `source_role_id → target_role_id`). **Nooit** een org→org *conclusie* opslaan ("X en Y zijn verweven"). Een mechanisme-loze relatie is géén verboden orphan meer maar een **kandidaat** (bottom-up): ze mag als `voorgesteld` incuberen (telt in niets; zichtbaar via `GET /api/kandidaten`, gegroepeerd op rol-paar A→B) maar kan **niet** naar `goedgekeurd` zolang er geen theorie-element bij hoort — de orphan-poort zit op het *goedkeur*-moment (`_modereer`), niet op creatie (een kandidaat landt dus altijd `voorgesteld`, ook van een maintainer). Zodra een rol-paar genoeg kandidaten verzamelt om de abstractie te dragen, dient een RfC (`nieuw_theorie_element`, mechanisme) het nieuwe mechanisme in én geeft die in zijn `instantiaties` óf **adoptie** van een kandidaat (`{"bestaande_relatie_id": N}`) óf een **verse** instantie (`{"source_id","target_id","relation_type",…}`) mee — bij acceptatie krijgt de kandidaat zijn mechanisme (verse instanties landen `voorgesteld`). Past wél een bestaand mechanisme? → zet het meteen, geen kandidaat. (De *verworpen* org→org-conclusies rel. 471/473/474 blijven verwijderwaardig: dat waren foute conclusies, geen kandidaten. De rolpaar-match wordt niet gevalideerd — instanties lopen losjes — maar dit is de bedoelde regel.)
2. **Litmus — directe edge vs. brug vs. veld.** Beslisvraag: *wisselt de persoon van werkgever (→ brug), of leent de instelling z'n stem uit (→ directe edge)?*
   - Persoon **wisselt** tussen organisaties (draaideur/baantjescarrousel) → modelleer `persoon↔org`-affiliatie-edges (instanties van `draaideurconstructie`), gedateerd; de org↔org-band is de **vanzelf afgeleide brug** (ongericht, beschrijvend; relatietypes in `BRUG_AFFILIATIE`: `lidmaatschap/bestuurder/adviseur/draaideur/personeel/woordvoerder_van`). **Nooit** een org→org draaideur-relatie. Een gedateerd paar geeft gratis de loopbaan-gantt.
   - Persoon spreekt **namens** de instelling (vertegenwoordiging/expertbron) → **directe** `instelling→media`-edge (Sourcing; `expert_legitimatie`/`denktank_levert_expert`/`woordvoerdersregie`). Géén brug, géén `persoon↔media`-affiliatie (een gastoptreden is geen lidmaatschap).
   - Staande toestand van één knoop zonder live-zender → `veld_eigenschap`; groepsbreed/feedback-lus → emergent hyperedge.
3. **"Hoe verweven zijn X en Y?"** wordt beantwoord door de **brug**, niet door een opgeslagen edge. Dubbelzinnige invloedsrichting (zoals een carrousel) → verzin géén gerichte invloedspijl; gebruik de brug (ongericht) + de verdedigbare gerichte filter-edge (coöptatie/zelfcensuur).
4. **Afgeleide (indirecte) pijlen zijn nooit een element.** Ze worden niet opgeslagen; ze vergen een padclaim (`property='indirecte_invloed_op'`) en zijn gepoort — in de praktijk dormant zolang invloed op de 0,05-vloer staat (het max-product van twee vloer-schakels haalt `DERIVED_MIN` nooit). Stel er dus geen voor als "element".
5. **Bron verifiëren vóór indienen — quotes verbatim checken; nooit fabriceren.** Een onbronbare claim komt **niet** binnen (eerlijk melden, geen `contextual` "niets gevonden"). Let op mis-attributie: een NOS-stuk uit 2013 bleek de *Eerlijke Bankwijzer* te crediteren i.p.v. PAX — alleen zichtbaar ná het ophalen van de exacte quote.
6. **Indienvolgorde** (account `assistent`, alles `voorgesteld`): bronnen (+locators) → entiteiten → relaties (mét `mechanism_id`) → argumenten (mét echte citaties). Instantielaag = één menselijke reviewer; theorielaag = RfC.

*Gewerkt voorbeeld (juni 2026).* De "PAX↔D66-baantjescarrousel" bleek na onderzoek niet te staven (geen D66-link; enige harde overlap = Farah Karimi, GroenLinks→PAX-RvT, ná haar Kamertijd). Uitkomst: org→org draaideur-relaties 471/473/474 horen weg; Karimi ging erin als persoon-entiteit + twee gedateerde affiliatie-relaties (instanties van `draaideurconstructie`) zodat de brug PAX↔GroenLinks vanzelf verschijnt; en "PAX levert experts/onderzoek aan de media" als directe `PAX→media` Sourcing-edge (rel. 530, `expert_legitimatie`) — drie schone verbanden, elk met eigen mechanisme/richting/weergave, géén indirecte pijl.

## Scripts conventions

All scripts resolve paths relative to the repo root via `Path(__file__).parent.parent` and assume `data/propaganda_model.db` exists (except `init_db.py`). Two families:

- `seed_*` — insert fresh data extracted from `sources/AI/*.md`.
- `migrate_*` / `enrich_*` — evolve an existing DB. Migration scripts copy the DB to `data/propaganda_model_backup_<timestamp>.db` before altering it (hence the backup files in `data/`). When changing the schema, follow this backup-then-migrate pattern rather than editing `schema.sql` alone, since real data already lives in the DB.

**Dogfood-regel (M0.6, geldt sinds juni 2026):** *inhoud* (argumenten, citaties, entiteiten, relaties, instantiaties, voorstellen, ratings — ook van de eigenaar, ook agent-werk) gaat uitsluitend via het bijdragepad: de REST API met een ingelogde gebruiker of Bearer-token (`data/tokens/<naam>.token`), zodat attributie en `edit_log` vanzelf kloppen. **Claude Code draagt zelf óók zo bij:** onder een *eigen* agent-account (`bijdrager`, eigen token in `data/tokens/`) — nooit met het account of token van de eigenaar, want dat zou de attributie laten liegen én de poorten omzeilen. Mergen/verifiëren (reviewer+), verwijderen (maintainer) en tellende reviewer-akkoorden blijven mensenwerk; alles wat de AI indient blijft `voorgesteld` tot een mens het beoordeelt (ik stel voor, jij beslist). Migratiescripts zijn voortaan alléén voor schema en structuur. Test-/kwaliteitsscripts: `scripts/validate_model.py` (checks in `validation.py`, shared with `/api/health`), `scripts/test_fresh_build.py` (verse build + alle endpoints), `scripts/test_auth_smoke.py` (poorten/attributie), `scripts/test_fase2.py` (voorstel-workflow, RfC's, samenvoegen/splitsen end-to-end), `scripts/test_fase3.py` (voorspellingsregister, onderzoeksagenda, releases end-to-end).

**Admin-pad via `scripts/admin.py` (maintainer-acties, geen *inhoud*):** keuren / afwijzen / herkeuren / editten / mergen en het lezen van de reviewer-gated adviesbestanden zijn géén inhoudsbijdrage en lopen daarom **niet** via het `assistent`-bijdragerspad, maar via een dunne REST-client: `scripts/admin.py` (stdlib `urllib`, géén DB-toegang — het wrapt enkel bestaande endpoints, er is dus **geen nieuwe API**). Subcommando's: `queue`, `advies` (`GET /api/review_advies`), `bronnen` (`GET /api/bron_suggesties`), `afgewezen`, `merge <id>`, `afwijzen <id> -m …`, `herkeuren <id> -m …`, `edit-arg <id> --claim/--reasoning`, `voorstel <id>`, `voorstel-akkoord <id>`, `voorstel-afwijzen <id> -m …`. Identiteit: het **`maxime`**-maintainer-token (`data/tokens/maxime.token`) — een *mens*-account. Dit is de **enige** plek waar Claude het eigenaars-token gebruikt, en uitsluitend voor admin-acties (de "nooit het token van de eigenaar"-regel hierboven geldt voor *inhoud*). De kernregel blijft staan: dit is de **eigenaar die via Claude handelt** — Claude voert admin-besluiten alleen uit op *expliciete aanwijzing* en keurt **nooit** ongevraagd zijn eigen `assistent`-inzending goed (ik stel voor, jij beslist; een maintainer-akkoord telt in de opbouwfase als volledig quorum, dus dat besluit blijft van de mens). De twee paden blijven gescheiden: inhoud *voorstellen* → `assistent` (bijdrager); admin → `maxime` (mens-maintainer). **Triggerwoord "via admin".** De "expliciete aanwijzing" hierboven heeft een vaste vorm: zegt de eigenaar **"via admin"** (bv. "merge via admin", "wijs af via admin", "keur goed via admin"), dán — en alléén dán — voer je de admin-actie meteen uit met het `maxime`-token (via `scripts/admin.py` of rechtstreeks het endpoint), zónder terug te vragen. Hoor je die woorden niet, dan geldt het normale pad: *voorstellen* via `assistent` en de merge aan de mens laten. Twee grenzen blijven ook bij "via admin" staan: (1) "via admin" ís het oordeel van de eigenaar, dus zet **nooit** ongevraagd je eigen `assistent`-inzending door omdat je zélf vindt dat ze goed genoeg is — de eigenaar moet de actie zelf benoemen; (2) je handelt *namens* de eigenaar, dus het `edit_log` schrijft terecht `maxime`, niet de agent. Dit geldt voor élke agent/sessie, niet alleen Claude Code.

**Releases (M3.1):** `releases/` is ingecheckt (anders dan `data/`): per release een onveranderlijk scores-snapshot (`model-vX.Y.Z.json`) + changelog met score-diff (`model-vX.Y.Z.md`), gemaakt door `scripts/release_model.py`. Het script commit/tagt niet zelf (of expliciet via `--tag`); de viz-topbar en `/api/health` tonen de nieuwste releasetag.

`sources/` holds raw research material (the `AI/` analyses are the primary extraction input); see `sources/README.md` for the `YYYY-MM-DD_speaker_topic.txt` naming convention.
